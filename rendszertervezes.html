1. Bevezetés

Jelen dokumentum a Visszhang (Echo) című, egyjátékos, lopakodásra és túlélésre építő horrorjáték rendszerterve. A játékos egy elhagyatott űrállomáson rekedt szerelőt irányít, a környezet feltárásával, tárgyak gyűjtésével, feladatok végrehajtásával és a lény elkerülésével próbál kijutni. A dokumentum a H4 rendszertervezési feladatához tartozik, és a tantárgyi rendszerterv-minta fejezetcímeit és sorrendjét alkalmazza.

A tervezés alapja az SRS (FR-01–FR-39, UC-01–UC-16), a felhasználói dokumentáció, a projektterv, a vízió, a szótár és az analízis modell. Utóbbi hét logikai alrendszert és 31 analízisosztályt különít el; a jelen dokumentum ezekhez rendeli a kezelőfelületi, adatmegőrzési és együttműködési megoldásokat.

Tervezési feltételezések: asztali, helyben futó, egyjátékos játék; nincs kötelező online fiók vagy szerverkapcsolat. Az SQLite és az adatbázist használó osztályok a jelen dokumentumban rögzített tervezési döntések, nem az SRS által előírt technológiák. A tényleges játékfejlesztő motor, programnyelv és végleges grafikai dizájn a megvalósítás során rögzíthető.

Legfontosabb minőségi szempontok: folytatható mentések (FR-32), korábbi érvényes állapot megőrzése hiba esetén (FR-33), az MI-szerepek elkülönítése (FR-16–FR-27), térbeli hangvisszajelzés (FR-35), átállítható irányítás, feliratozás, több felbontás támogatása (FR-36–FR-39).

2. Felhasználói felület

Az egységes kezelőfelület célja, hogy a játékos a játékmenet során elsősorban a világra figyeljen. A HUD csak alapvető állapotinformációkat jelenít meg; a részletes célok, bejegyzések és tárgyak külön megnyitható nézetekben érhetők el. A képernyőtervek semlegesek: elrendezési tervek, nem végleges grafikai képernyőképek.

3. Adatmodellek

Az alkalmazás helyi perzisztens adatokat kezel: mentési helyek és állapot-pillanatképek, valamint felhasználói beállítások. A világ statikus tartalma (pályadefiníciók, feladat- és tárgysablonok, hangadatok) verziózott játékerőforrásként érkezik; az adatbázisban ezekre azonosítóval hivatkozó állapot tárolódik. Az MI pillanatnyi döntési állapotát is a mentési csomag tartalmazza, de sem érzékelési, sem rendező-MI naplózás nem használható illegitim játékoskoordináta átadására.

3.1 Adatbázis kezelő kiválasztása

Tervezési döntés: a kliensgépbe ágyazott SQLite adatbázis használata. Indoklás: egyjátékos alkalmazás, offline működés, tranzakciók, egyszerű telepítés, táblás sémával ellenőrizhető mentési metaadatok; nem szükséges külön adatbázisszerver. Ez nem ütközik az SRS-sel, amely technológiát nem köt meg. A motor és a programnyelv kiválasztásától függően szabványos SQLite driver vagy adapter biztosítja az elérést.

A kapcsolattartás a SaveRepository, SettingsRepository, DatabaseConnection és SchemaMigrator osztályokon keresztül történik. A játékmenet kizárólag a SaveService alkalmazási szolgáltatással kommunikál; közvetlen SQL-hívást nem végez.

Hibabiztonság: az új állapotot egy tranzakcióban kell rögzíteni; előbb ellenőrzött állapotcsomag készül, és csak sikeres INSERT/UPDATE + COMMIT után jelölhető aktívként. Sikertelen műveletkor ROLLBACK, az utolsó ellenőrzött mentés megmarad. Az adatbázis integritását idegen kulcsok és ellenőrzőösszeg támogatják. A biztonsági mentés nem azonos a játékbeli mentési hellyel.

3.2 Szemantikai adatmodell

A mentés egy adott játékfutás meghatározott pillanatának konzisztens állapotát tartalmazza. Az egyszerű kezelhetőség érdekében a dinamikus részrendszer-állapotokat egyetlen, szerializált és verziózott payload pillanatképben tároljuk. A fejlécek, mentési helyek és játékosbeállítások relációs mezőkkel is lekérdezhetők. Ez a hibrid modell logikailag külön kezeli a tartalmi entitásokat, de nem kényszeríti az MI-változókat tucatnyi szorosan csatolt táblába.

3.3 Relációs adatmodell

Az ER-modellből öt tábla lesz. A kapcsolatok kulcsokkal és megszorításokkal rögzítettek. A save_snapshot sorok verziózott pillanatképei lehetővé teszik, hogy egy felülírt mentési hely korábbi érvényes állapota megmaradjon. A képernyő alapértelmezés szerint az adott mentési hely legfrissebb érvényes pillanatképét mutatja.

PRAGMA foreign_keys = ON;

CREATE TABLE player_profile (
  profile_id TEXT PRIMARY KEY,
  display_name TEXT NOT NULL
);

CREATE TABLE user_settings (
  profile_id TEXT PRIMARY KEY REFERENCES player_profile(profile_id),
  settings_version INTEGER NOT NULL CHECK(settings_version > 0),
  settings_json TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE game_run (
  run_id TEXT PRIMARY KEY,
  profile_id TEXT NOT NULL REFERENCES player_profile(profile_id),
  started_at TEXT NOT NULL
);

CREATE TABLE save_slot (
  slot_id TEXT PRIMARY KEY,
  profile_id TEXT NOT NULL REFERENCES player_profile(profile_id),
  slot_label TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE(profile_id, slot_label)
);

CREATE TABLE save_snapshot (
  save_id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL REFERENCES game_run(run_id),
  slot_id TEXT NOT NULL REFERENCES save_slot(slot_id),
  created_at TEXT NOT NULL,
  schema_version INTEGER NOT NULL CHECK(schema_version > 0),
  scene_id TEXT NOT NULL,
  play_time_seconds INTEGER NOT NULL CHECK(play_time_seconds >= 0),
  progress_percent INTEGER CHECK(progress_percent BETWEEN 0 AND 100),
  payload_json TEXT NOT NULL,
  checksum_sha256 TEXT NOT NULL,
  validation_status TEXT NOT NULL DEFAULT 'valid'
    CHECK(validation_status IN ('valid','invalid'))
);

CREATE INDEX idx_save_slot_date ON save_snapshot(slot_id, created_at DESC);
CREATE INDEX idx_game_run_profile ON game_run(profile_id);

Konverzió: a PLAYER_PROFILE–GAME_RUN és PLAYER_PROFILE–SAVE_SLOT 1:N kapcsolatok idegen kulcsként szerepelnek a gyermektáblákban; a USER_SETTINGS 1:0..1 kapcsolat a profilazonosítót közös elsődleges és idegen kulcsként használja; a GAME_RUN–SAVE_SNAPSHOT és SAVE_SLOT–SAVE_SNAPSHOT kapcsolatok két kötelező idegen kulccsal reprezentáltak. A mezők azonosítói stabilan tárolt UUID-k lehetnek; az időpontok UTC ISO 8601 karakterláncok.

Integritási többletszabály: egy mentés run_id és slot_id értéke csak azonos profilhoz tartozhat; ezt a SaveRepository ellenőrzi ugyanabban a tranzakcióban. A checksum_sha256 a kanonizált payload_json bájtjaira vonatkozik; a hash nem titkosítás vagy hitelesítés. Beolvasáskor a tartalmi séma és a hivatkozott játékerőforrások érvényességét is ellenőrizni kell.

3.3.1 Példák a lekérdezésekre

-- A kiválasztott mentési hely legfrissebb érvényes állapota:
SELECT save_id, created_at, scene_id, progress_percent, payload_json, checksum_sha256
FROM save_snapshot
WHERE slot_id = :slot_id AND validation_status = 'valid'
ORDER BY created_at DESC, save_id DESC
LIMIT 1;

-- Mentések listája (metaadatok; a payloadot a listázás nem tölti be):
SELECT s.slot_id, s.slot_label, v.created_at, v.scene_id, v.progress_percent
FROM save_slot s
LEFT JOIN save_snapshot v ON v.save_id = (
  SELECT x.save_id FROM save_snapshot x
  WHERE x.slot_id = s.slot_id AND x.validation_status = 'valid'
  ORDER BY x.created_at DESC, x.save_id DESC LIMIT 1
)
WHERE s.profile_id = :profile_id;

4. A funkcionális modell kiegészítése

Az analízis modell statikus és dinamikus modelljeit az alábbi végrehajtási forgatókönyvek egészítik ki, az adatáramlás, alternatív ágak és kivételes helyzetek részletezésével.

4.1 Mentés folyamat

Előfeltétel: a játék állapota stabil mentési pillanatképként kiolvasható; a játék a kiválasztott mentési politikát megengedi.

Normál ág:

  1. A felület a SaveLoadView komponensen keresztül mentést kezdeményez.
  2. A SaveService kiolvassa a világállapotot.
  3. A SnapshotCodec ellenőrzi és szerializálja az állapotot.
  4. A SaveRepository tranzakcióban új save_snapshot sort hoz létre.
  5. Csak a sikeres COMMIT után jelenik meg a sikerüzenet.

Hibaág: sérült állapot, megtelt háttértár, SQL-hiba vagy ellenőrzési hiba esetén ROLLBACK és célzott hibaüzenet; az előző mentési sor változatlan marad.

Utófeltétel: egy mentés teljes és ellenőrizhető, vagy nincs látható félkész módosítás. Kapcsolódás: FR-32–FR-34, UC-08.

4.2 Betöltés folyamat

  1. A felület listázza az érvényes mentések metaadatait.
  2. A kiválasztott save_id rekord tartalma a kódoló-ellenőrző modulhoz kerül.
  3. A checksum, a schema_version, a kötelező állapotblokkok és a játékerőforrás-azonosítók ellenőrzése után a világ egy ideiglenes állapotmodellbe épül fel.
  4. A lény-MI állapota csak a saját legitim észlelési memóriáját tartalmazhatja; a rendező-MI saját időzítőiből és feszültségbecsléséből áll helyre.
  5. Csak teljes siker esetén cserélődik az aktív játékvilág az ideiglenesre, valamint újraindulnak a megfelelő hang- és felületi komponensek.
  6. Érvénytelen mentés esetén az aktív játékvilág nem módosul; a felület hibát jelez, és egy korábbi érvényes pillanatképet kínálhat.

Kapcsolódás: FR-32–FR-33, UC-01 és UC-08.

4.3 Beállítások módosítása

A beállítási felület szerkeszthető munkapéldányt tart fenn. Mentéskor ellenőrzi a határértékeket, a kötelező vezérlési műveletek kiosztását és a képernyőn elérhető UI-elemeket. A sikeres adatbázis-tranzakció után alkalmazza a hang-, vezérlés-, felirat- és méretezési beállításokat. Ha bármelyik alkalmazási lépés sikertelen, visszaállítja a korábbi, működő konfigurációt, és érthető hibaüzenetet ad. A felbontásváltozás csak visszaigazolás után válhat véglegessé. Kapcsolódás: FR-36–FR-39, UC-10.

4.4 Lény-MI és rendező-MI adatáramlása

Világbeli események (zaj, fény, mozgás)
    --> Érzékelési modell (látás, hallás)
        --> Lény-MI (legitim észlelési memória)
            --> Világállapot : mozgás / támadás

Világbeli események (aggregált játékesemény)
    --> Rendező-MI (feszültség, ritmus)
        --> Környezeti eseményvégrehajtó
            --> Világállapot : fény/zaj módosítás

Világállapot --> Világbeli események : fizikai esemény

A rendező-MI világállapotból és eseménystatisztikákból feszültséget becsül, és lehetséges környezeti történéseket kér. Nem adhat át közvetlen, a lény számára nem észlelt játékospozíciót, nem állíthatja át a lény célpontját kikerülve az érzékelési logikát. Ha a rendező zajt generál, a lény kizárólag a ténylegesen létrejött, hallható zajt észlelheti, és annak helye felé vizsgálódhat. A világ fizikai korlátait a mozgás- és útkereső rendszer végig érvényesíti. Kapcsolódás: FR-16–FR-27; UC-11–UC-16.

4.5 Térbeli hang és vizuális megfelelő

Minden releváns hang eseményként érkezik a hangrétegbe: sourceId, forráspozíció, típus, erősség, időbélyeg és opcionális feliratszöveg. A játékos és a kamera transzformációjából kiszámítható a relatív irány és távolság, majd ebből a hangerő, panoráma és az elérhető audioeszközzel a térbeli leképezés. A kritikus hangokhoz felirat és választható irányjelzés is társul. Mentés után az egyszeri hangokat nem feltétlenül kell újra lejátszani; a folyamatos források és a hangkörnyezet állapota rekonstruálandó. Kapcsolódás: FR-35 és FR-38.
